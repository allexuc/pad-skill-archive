# パズドラ スキルアーカイブ

モンスター約1.4万体、アクティブ・リーダー合わせて約1.6万種のスキル。
元データが日次更新なので件数は増えていく。
スキルから所持キャラ（図鑑番号つき）を、キャラ名からスキルを、どちらからでも引ける。

## 中身

| ファイル | 用途 |
|---|---|
| `pad_skill_archive.html` | 単一HTMLの検索UI。ダブルクリックで開くだけ。オフラインで動く |
| `pad_archive.sqlite` | SQL用。FTS5 trigram つきで日本語の部分一致が効く |
| `build_pad_archive.py` | 元データ取得 → SQLite / 圧縮JSON |
| `build_archive_html.py` | 圧縮JSON → 単一HTML |
| `update-archive.yml` | 週次で最新に追従する GitHub Actions ワークフロー |
| `.gitignore` | 中間生成物をコミットしないための除外設定 |
| `mycategories.json` | マイカテゴリの初期値。ビルド時にHTMLへ焼き込まれる |
| `awakening_names.json` | 覚醒ID → 日本語名。全種入力済み |
| `awoken.png` | 覚醒アイコンのスプライト。無ければビルド時にGitHubから取得する |

## データの素性

出典は [Mapaler/PADDashFormation](https://github.com/Mapaler/PADDashFormation) の
`monsters-info/`（`mon_ja.json` と `skill_ja.json`）。**日次で更新されている**。

前回調べた DadGuide 系（2023年4月で凍結）とは別系統で、こちらは現行データ。
日本語のスキル名・説明文がそのまま入っているうえ、初期の溜まりターンも取れる。

```bash
python build_pad_archive.py --remote out
python build_archive_html.py out/archive.json.gz out/pad_skill_archive.html
```

引数なしでGitHubから直接取ってくるので、リポジトリ全体（2.2GB ある）を
clone する必要はない。取得するのは JSON 2本で約26MB。

`update-archive.yml` を `.github/workflows/` に置けば毎週月曜の朝に自動で回る。

### コミットするのは HTML だけにしてある

1回の生成物は HTML 1.56MB + SQLite 16MB + gz 1.08MB で **18.7MB**。
これを週次で1年積むと **約0.95GB** になり、リポジトリが持たない。
HTML は自己完結しているので、ワークフローは `docs/pad_skill_archive.html` だけを
コミットし、SQLite と gz は `build/` に置いて捨てる。

SQLite も配りたい場合は、ワークフロー末尾にコメントアウトしてあるリリース添付を使う。
リリース添付なら履歴には残らない。

GitHub Pages を `docs/` にすればそのまま公開できる（HTML 単体で動く）。

## 3つのタブ

| タブ | 1行の単位 | 用途 |
|---|---|---|
| **キャラ** (既定) | モンスター 約14,000 | アクティブ・リーダー・覚醒をまとめて絞る |
| アクティブスキル | スキル 約8,800 | スキル単位で重複なく見る |
| リーダースキル | スキル 約7,600 | 同上 |

アクティブ・リーダー・覚醒はデータ上どれもモンスターにぶら下がっているので、
**行をキャラに揃えると3つを同時に絞り込める**。それが「キャラ」タブ。
1行の中にアクティブとリーダーを左右に並べ、上に覚醒アイコンを出している。

例:

| 条件 | 該当キャラ |
|---|---|
| スキル文に「[ロック]を解除」 | 4,800 |
| ＋ 覚醒アシストを持つ | 1,275 |
| ＋ リーダーの攻撃倍率が×10以上 | 13 |

いずれも SQLite に同じ条件を投げた結果と一致することを確認済み。
検索語はキャラ名・スキル名・スキル文のどれに当たっても拾う。
カテゴリはアクティブ側とリーダー側の語彙を名前で1本にまとめてある。

スキル単位で重複なく見たいとき（「この効果のスキルは何種類あるか」
「同じ効果で一番CDが軽いのはどれか」）は元の2タブを使う。

## アクティブとリーダーは完全に別物

図鑑データ上、アクティブスキルIDとリーダースキルIDの集合は**重複がゼロ**だった
（件数は日次で増えるが、共通IDは常に無い）。なので推測ではなく、データそのものに沿って
タブで分けている。タブごとに検索語・属性・カテゴリを別々に保持する。

## 画面の構成

ページ全体が下方向にスクロールする。**固定されるのは検索欄だけ**（約48px）。
タブ・検索対象・属性・並び順・カテゴリはすべて結果と一緒に流れていく。
スクロールすると画面の 94%（デスクトップ 95%）が結果に使える。

以前はタブと検索対象も固定していたが、モバイルで172px＝画面の2割を
占めていたので、検索欄だけに絞った。入力欄の高さも47px→37pxに詰めてある。
ただしモバイルでは文字サイズを16pxに保っている。iOS は16px未満の入力欄に
フォーカスすると画面を勝手に拡大するため。

出典や注意書きは常設せず、右上の「この表の見かた」に畳んである。

「覚醒で絞る」「カテゴリを広げる」は、それぞれが開く帯の**直上**に置いてある
（帯の25px上）。どのボタンがどの帯に効くかを近さで示すため。
開いている間はボタンの見た目が変わる（`aria-expanded`）。

## 検索のしかた

- **スキル文** … ゲーム内表記は `[火]` のように角括弧つきだが、括弧を外して入力しても当たるようにしてある。`ロックを解除` でも `[ロック]を解除` でも 3,003 件
- **キャラ名** … `ツバキ` で、そのキャラたちが持つスキルに絞れる
- **数字だけ** … 図鑑番号かスキルIDの完全一致。`3000` で No.3000 の持つスキルが出る
- **検索対象**（キャラタブのみ） … 検索欄の上で **すべて / キャラ名 / アクティブ / リーダー**
  を切り替えられる。1行にアクティブとリーダーが同居しているので、どちらに当てるか選べる。
  例: 「コンボ加算」はアクティブ838体・リーダー2,567体で、混ぜると3,268体になる
- **タイプ** … 属性の隣。複数選ぶと AND（ドラゴン＋神で306体）。
  スキルタブでは「そのタイプをすべて持つキャラが1体でも所持しているスキル」に絞る。
  進化用・覚醒用・強化合成用・売却用の素材系は普段使わないので既定で畳んである
  （「素材…」で開く）。選んだまま隠れると理由の分からない絞り込みになるため、
  素材タイプを選んでいる間は自動で開いた状態になる
- `/` キーで検索欄にフォーカス

絞り込みはタブごとに別。アクティブ側は**最短CD の上限**、リーダー側は**攻撃倍率の下限**。

## スキルのCD表示

`CD 8 → 3` は「スキルレベル1で8ターン、最大レベルで3ターン」の意味。
スキルレベルが1上がるごとに1ターン短くなるので、
最短CD = 初期CD −（最大レベル − 1）で求まる。
レベルアップで縮まないスキル（最大レベル1）は `CD 18` のように1つだけ出る。

アクティブスキル全件で最短が1ターン未満にならないことを確認済み。

**絞り込みと並び替えは最短CDを基準にしている。** 実際に運用するのは
最大レベルなので、そちらの方が使える条件になるため。
SQLiteでは `cooldown`（レベル1）と `cooldown_min`（最大レベル）の両方を持つ。

## 並び順

既定は**新しいキャラ順**。1つのスキルを複数キャラが持つので、
**所持キャラのうち最大の図鑑番号**を基準に降順にしている。

| 選択肢 | 基準 |
|---|---|
| 新しいキャラ順 | 所持キャラの最大図鑑番号の降順（既定） |
| 古いキャラ順 | 所持キャラの最小図鑑番号の昇順 |
| 所持キャラ数 | 持っているキャラが多い順 |
| スキルID順 | スキルIDの昇順 |

所持キャラのチップは先頭8体までしか出さないので、並び順の基準になったキャラが
隠れないようチップの向きも並び順に合わせてある。並び順もタブごとに独立。

キャラタブは行がキャラなので、同じ選択肢でも基準が変わる。
実態に合わせて選択肢の名前も差し替えている。

| スキルタブ | キャラタブ |
|---|---|
| 所持キャラ数 | 覚醒の多い順 |
| スキルID順 | 最短CDの短い順 |

## チップを押しても画面が動かない

カテゴリ・覚醒・マイカテゴリのチップを押すと絞り込みが走り、結果を先頭から描き直す。
以前はそのたびにページ先頭へ戻していたので、チップを押すと画面が跳ねていた。

いまは深くスクロールしていたときだけ結果の先頭まで引き戻す。
チップは結果より上にあるので、**押したチップが見えている限り画面は1pxも動かない**。

## 生成物の検査

ワークフローには、生成されたHTMLに主要な機能が入っているか確かめるステップがある。
スクリプトの更新漏れに気づかないままコミットするのを防ぐための歯止めで、
足りない機能があればその場で失敗して名前を出す。

```
生成物に次の機能が入っていません:
  - タッチ端末の自動フォーカス抑止
  - キャラ統合タブ
build_archive_html.py が古い可能性があります。
```

## 覚醒

覚醒は138種が使用中（2026年10月時点）。ゲーム側に追加されると増える。
独立したタブは廃止し、「キャラ」タブに統合した。

- 「覚醒で絞る」を押すと引き出しが開く。複数選ぶと AND
- キャラタブでは超覚醒も含めてそのキャラ自身の覚醒で判定する
- 超覚醒は「超」の仕切りの右側に分けて表示

### 並び順は名前で束ねてある

出現頻度順だと関連するものが散らばるので、名前で13グループに分けている。

| グループ | 件数 |
|---|---|
| キラー | 12 |
| 操作時間 | 2 |
| 耐性 | 11 |
| スキル・アシスト | 9 |
| ドロップ強化 | 8 |
| 属性強化 | 10 |
| コンボ | 15 |
| 消し方 | 9 |
| 多色 | 10 |
| 貫通・追撃 | 6 |
| タイプ・副属性 | 13 |
| 回復・軽減 | 11 |
| ステータス強化 | 20 |

回復とダメージ軽減はどちらも耐久側なのでひとまとめ。
浮遊・陽の加護・陰の加護・熟成・アフタヌーンティー・アシスト共鳴・自力・加速のように
名前の形からは行き先が決まらない常時効果はステータス強化に寄せてある。
ダンジョンボーナスはスキル・アシストに置いた。

グループ内はゲーム側のID順に近づけつつ、`X` と `X＋` が隣り合うようにしてある。
具体的には「基本名（末尾の＋を外したもの）が最初に現れたID」を第一キー、
実IDを第二キーにして並べている。これで属性強化なら
`火 → 火＋ → 水 → 水＋ → …` の順になる。

分類のルールは `build_pad_archive.py` の `AWAKENING_GROUPS` にある。
上から順に当てはめて最初に当たったグループに入るので、順序が意味を持つ。
全種が重複なく割り当たることをビルド時に確認できる。

一覧はアイコンだけを出し、名前と件数はツールチップに寄せた。
名前で探したいときは引き出し上部の入力欄で絞れる。

指で操作したときは、引き出しを開いても入力欄へ自動フォーカスしない。
ソフトキーボードがせり上がると肝心の選択肢が隠れてしまうため。

判定は2段構え。

1. `(any-hover: hover) and (any-pointer: fine)` が偽なら、指しか使えない端末とみなして常に抑止
2. マウスと指を併用できる端末では、そのクリックの `pointerType` で決める

`any-` を使うのは主入力ではなく「マウス等が繋がっているか」を見たいから。
`hover`/`pointer` だとタッチ対応PCが主入力=指と判定され、マウス操作でも指扱いになる。
1 を先に見るのは、環境によって合成クリックの `pointerType` が `mouse` になることがあり、
それでスマホにキーボードが出るのを防ぐため。

この挙動は `build_archive_html.py` の中にあるので、ワークフローで再生成しても消えない。
消えていないことは「生成物の検査」で毎回確かめている。

### 覚醒名について

ID 1〜106 は TsubakiBotPad/pad-data-pipeline の
`etl/pad/storage_processor/awoken_skill.json` 由来。
107以降はそこに無いので手入力で補っている。

名前が分からない新規IDは、アイコンと所持キャラの覚醒構成から特定する。
攻略サイトに載っているキャラの覚醒一覧と、`monster_awakenings` から出した
構成（超覚醒を含む全スロット）を突き合わせれば、未登録IDの位置が特定できる。
2キャラ以上で一致を確認してから登録する。

### ゲーム側に覚醒が追加されたら

`awakening_names.json` に `{"id": N, "name": "○○", "count": 0}` を足す。
`count` は参考値なのでビルドでは読まない。

名前を足すまでの間も画面からは消えない。名前表に無いIDは
**「新規・未確認」グループ**にアイコンだけで並び、絞り込みにも使える。
ビルド時にも警告が出る。

```
覚醒 139 種が使用中 / 名前表 136 件
  名前が未登録: [145, 146, 147]
```

アイコンは `awoken.png` から引くので、**覚醒が増えたらスプライトの更新も要る**
（コマ数が増えるため）。`awoken.png` を消しておけばビルド時にGitHubから取り直す。

アイコンは現行データ（Mapaler/PADDashFormation の `images/awoken.png`）から
IDで引いている。名前を直したい場合は `awakening_names.json` の `name` を書き換える。
`count` は所持キャラ数の参考値で、ビルドでは `id` と `name` しか読まない。

```json
{"id": 111, "name": "超コンボ強化＋", "count": 1648}
```

## 覚醒とスキルをまとめて絞る

アクティブ／リーダーのタブに「覚醒で絞る」を置いた。押すと引き出しが開く。

- 覚醒を選ぶと、**その覚醒をすべて持つキャラが所持しているスキル**に絞られる
- スキル文の検索・カテゴリ・属性・初期CD などと同時に効く
- 覚醒名で候補を絞れる（`コンボ` と打つと15件まで減る）
- 件数はそのタブで何件のスキルが該当するかを出している
- 選択状態はタブごとに独立

例（アクティブタブ）:

| 条件 | 件数 |
|---|---|
| 全体 | 8,808 |
| ダメージ無効貫通＋を持つキャラ | 1,292 |
| ＋ スキル文に「[ロック]を解除」 | 716 |
| ＋ スキルブースト+ も持つキャラ | 580 |

いずれも SQLite に同じ条件を投げた結果と一致することを確認済み。

覚醒タブ（行がモンスター）はそのまま残してある。
「この覚醒を持つキャラは誰か」を見るときはそちら、
「この覚醒を持つキャラのスキルは何か」を見るときはこちらを使う。

## アシストで絞り込む

覚醒アシストを持つキャラはアシスト運用されるので、
アクティブ／リーダーの両タブに **指定なし / アシストのみ / アシスト以外** の3択を置いた。

- 判定は「そのスキルを持つキャラの中に覚醒アシスト持ちが1体でもいるか」
- 所持キャラのチップにも `アシスト` の印がつく
- アクティブ 8,808 件のうち アシストのみ 3,755 / アシスト以外 5,053
  （2026年8月時点。データ更新で変わる）

覚醒アシストのIDは直書きせず `awakening_names.json` で `名前 == "覚醒アシスト"` の
エントリから引いている。名前表を差し替えても追随する。

## マイカテゴリ

自動分類とは別枠で、自分でカテゴリを足したり消したりできる。UIの黄色い帯がそれ。

- **＋ 追加** … 名前とキーワードを入れると新しいカテゴリになる。キーワードは正規表現も書ける（`変身|転生` のように）。入力中に該当件数が出るので、当たり具合を見ながら決められる
- **対象** … 両方のタブ／アクティブのみ／リーダーのみ を選べる。選んだタブにしかチップは出ない
- **削除** … チップ右の `×`
- **絞り込み** … チップを押すと自動カテゴリと同じく AND で効く
- **手動で入れる** … キーワードで表せないものは、各行の「＋ マイ」から個別に放り込める。入れた件数は `★ N` で出る

キーワードにマッチしたスキルと、手動で入れたスキルの **和集合** がそのカテゴリの中身になる。

### 保存のされ方

ブラウザの localStorage に入る。同じ端末で同じ場所のファイルを開く限りは残るし、
ビルドし直しても消えない。ただし別の端末には引き継がれない。

引き継ぎたいときは「JSON」ボタンで中身を出して、`mycategories.json` に貼る。
次のビルドから初期値として焼き込まれるので、GitHub Actions で回している場合も維持される。

```bash
python build_archive_html.py out/archive.json.gz out/pad_skill_archive.html mycategories.json
```

`mycategories.json` の形式:

```json
[
  {"name": "変身", "pattern": "変身", "scope": "active", "ids": []},
  {"name": "無効貫通", "pattern": "ダメージ無効を貫通", "scope": "both", "ids": []},
  {"name": "7×6マス", "pattern": "7[×x]6", "scope": "both", "ids": []}
]
```

`scope` は `both` / `active` / `leader`、`ids` は手動で入れたスキルID。
ビルド時に name の有無と pattern の正規表現としての妥当性を検査する。

## 目安として使う項目

- **属性オーブ** … スキルタブではスキル文中の属性語からの推定で、厳密な属性判定ではない。
  キャラタブでは図鑑の属性そのものなので推定ではない。
  なお回復（ピンク）はドロップの種類であってモンスターの属性ではないため、
  キャラタブでは表示しない（押しても必ず0件になる）
- **カテゴリ** … 説明文の正規表現マッチによる自動分類。`build_pad_archive.py` の
  `ACTIVE_RULES` / `LEADER_RULES` を書き換えれば自分好みに調整できる
- **説明文** … 元データには `^ff3600^`（色指定）`^qs^`（装飾開始）`^p`（解除）という
  装飾コードが 1,461 件混ざっているので、ETL 側で除去している
- **最大 ×N** … 説明文の「攻撃力がN倍」から拾った最大値。複合条件のリーダースキルでは
  実際に出せる倍率とは一致しない

**所持キャラと図鑑番号は図鑑データそのもの**なので、ここだけは推定ではない。
同じ内容は画面右上の「この表の見かた」からも読める。

## SQL で引く

```sql
-- あるスキルを持つキャラを図鑑番号つきで
SELECT m.monster_id, m.name, m.attrs
FROM skill_holders h JOIN monsters m ON m.monster_id = h.monster_id
WHERE h.kind='active' AND h.skill_id = 2637
ORDER BY m.monster_id;

-- キャラ名からスキルを逆引き
SELECT m.monster_id, m.name, s.kind, s.name, s.description
FROM monsters m
JOIN skill_holders h ON h.monster_id = m.monster_id
JOIN skills s ON s.rowid = h.rowid
WHERE m.name LIKE '%ヤマトタケル%';

-- 初期CD5以下でロック解除できるアクティブ
SELECT s.skill_id, s.name, s.cooldown, s.description
FROM skills s JOIN skill_categories c ON c.rowid = s.rowid
WHERE s.kind='active' AND s.cooldown <= 5 AND c.category = 'ロック解除'
ORDER BY s.cooldown;

-- 全文検索（trigram なので部分一致が効く）
SELECT s.skill_id, s.name, s.description
FROM skills_fts f JOIN skills s ON s.rowid = f.rowid
WHERE skills_fts MATCH '無効貫通';

-- 所持キャラが多い順
SELECT skill_id, name, holder_count FROM skills
WHERE kind='active' ORDER BY holder_count DESC LIMIT 20;

-- アシスト運用されるキャラが持つアクティブスキル
SELECT DISTINCT s.skill_id, s.name, s.description
FROM skills s JOIN skill_holders h ON h.rowid = s.rowid
JOIN monsters m ON m.monster_id = h.monster_id
WHERE s.kind = 'active' AND m.is_assist = 1
ORDER BY s.skill_id DESC LIMIT 20;

-- ある覚醒を持つキャラ
SELECT m.monster_id, m.name FROM monster_awakenings ma
JOIN monsters m ON m.monster_id = ma.monster_id
JOIN awakenings a ON a.awakening_id = ma.awakening_id
WHERE a.name = '封印耐性' ORDER BY m.monster_id DESC LIMIT 20;

-- 覚醒の組み合わせで絞る（両方持つキャラ）
SELECT count(*) FROM (
  SELECT monster_id FROM monster_awakenings
  WHERE awakening_id IN (SELECT awakening_id FROM awakenings
                         WHERE name IN ('封印耐性','操作時間延長+'))
  GROUP BY monster_id HAVING count(DISTINCT awakening_id) = 2);

-- 新しいキャラ順（UIの既定と同じ並び）
SELECT s.skill_id, s.name, s.newest_monster_id, m.name
FROM skills s JOIN monsters m ON m.monster_id = s.newest_monster_id
WHERE s.kind='active' ORDER BY s.newest_monster_id DESC LIMIT 20;
```
